# 由 AI agent 團隊進行產品審查

一份企劃在交給設計師或工程師之前，必須先通過一連串挑戰。其中好幾位挑戰者是 AI agent（能自主執行任務的 AI 助手），各自扮演不同角色。這是我為團隊制定的發布流程。

## 流程：8 個階段，每一關都是檢驗

| 階段 | 做什麼 | 必須產出什麼 |
|---|---|---|
| 1. 定義問題 | 核心問題、如何衡量成功，以及每個重要功能的一句話價值說明 | 一頁式發布目標 |
| 2. 精簡 | 一個 AI agent 用第一性原理思考：什麼必須保留、什麼可以更簡單、什麼可以晚點做、什麼應該砍掉 | 更精簡的企劃，以及後續功能的路線圖 |
| 3. 撰寫規格初稿 | 使用者故事、運作方式、使用者體驗、決策紀錄 | 初稿 |
| 4. 模擬 NPS | 模擬使用者為企劃評分。**如果預期 NPS 為負，就退回第 3 階段** | NPS 報告 |
| 5. 四角色挑戰 | 四個 AI agent 分別扮演**產品經理、設計師、營運和品牌**，各自獨立挑戰同一份企劃 | 待修正問題清單 |
| 6. 設計前品質檢查 | 一個 AI 檢查員審查邏輯：每條使用者路徑都涵蓋到了嗎？每個畫面的所有狀態（空白、載入中、錯誤）都有嗎？分支都完整嗎？ | 修正後的規格 |
| 7. 鎖定範圍 | 依風險拆分、鎖定範圍，並為每個功能訂定**淘汰規則**：上線 4 週後衡量什麼，以及低於哪個水準就移除 | 鎖定的範圍 |
| 8. 做或不做 | 依照檢查清單做最終審查 | 決定開發 |

## 讓 AI 審查者真正有用的規則

**每個審查者只有一個明確角色。** 「幫我審查一下」只會得到客氣、籠統的回饋。「你是每天都要負責營運這個功能的營運主管；列出哪些地方會出問題」才會得到具體的問題。

**審查者各自獨立作業。** 四個角色 agent 看不到彼此的意見，所以不會只是互相附和。

**數字必須有真實來源。** 如果規格中的基準數字在每週數據快照裡找不到，品質檢查員就會判定不通過。AI 寫作工具很擅長產生看起來很合理的數字，這條規則能防止編造的數據混進決策。

**負面結果是硬性喊停；正面結果不等於過關。** 為什麼 AI 審查者太樂觀，請見 [AI 模擬使用者測試](../ai-user-simulation/README.md)。

**創辦人視角只提建議，沒有否決權。** 反映創辦人思考方式的 agent 可以提出他們最在意的三個疑慮，但不能單獨否決一份企劃。

## 實務案例

在一次設計審查中，六個 agent 挑戰了一份推播通知的企劃。企劃有兩個選項：固定訊息範本，或讓 AI 撰寫每一則訊息。agent 們的結論是**兩個都不對**：範本讀起來很機械化，完全由 AI 撰寫的訊息又難以控管。重點在於，直到 agent 們把兩個選項都挑戰過一輪，正確答案才浮上檯面。

## 給想嘗試這套做法的團隊的建議

- AI 審查者很便宜，所以要早點用，別等設計師在錯的方向上花了一週。
- 價值來自**角色之間的衝突**，而不是某一個聰明的審查者。
- 最後一定要由人來決定。agent 負責找問題，人負責做決定。

---

*流程和規則由我設計。大部分審查工具（規格撰寫器和品質檢查員）由同事開發，四個角色 agent 則由產品團隊建置。*
