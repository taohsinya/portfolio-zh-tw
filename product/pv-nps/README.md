# 感知價值與 NPS：用數字決定要做什麼

## 規則

每個功能要進入開發，都必須通過兩項檢驗：

| 檢驗 | 問題 | 少了它會出什麼問題 |
|---|---|---|
| **感知價值（PV, Perceived Value）** | 使用者會因為這個功能而付費嗎？ | 體驗不錯，但沒人願意付錢 |
| **NPS（淨推薦值, Net Promoter Score）** | 體驗好到使用者願意推薦給別人嗎？ | 功能有價值，但流程太慢或太難懂，大家就不用了 |

如果無法證明一個功能能提升這兩個分數之一，我們就不做。任何人的意見，包括我自己的，單獨都不算數。

## 如何評估感知價值

PV 不是「產品經理覺得很重要」。它來自兩個問題。

**1. 消失測試。** 如果這個功能明天消失，使用者會怎麼做？
- 找替代品 → 價值低
- 將就著用 → 價值中等
- 無法接受 → 價值高

**2. 免費替代測試。** 有沒有免費產品能做到這個功能的 80%？
- 有 → 價值低：我們只是「也有這個功能」
- 沒有 → 價值高：使用者只能從我們這裡得到

接著，每個功能都依照固定的評分基準打分，讓不同的人評出一致的分數：

| 分數 | 使用者會怎麼說 | 使用者會怎麼做 |
|---|---|---|
| 9–10 | 「如果它消失了，我會付錢買別的產品來取代」 | 尋找替代品，接受更高的價格 |
| 7–8 | 「我會很不爽，而且願意付錢保留它」 | 在付費牆前猶豫，最後付費 |
| 5–6 | 「會覺得可惜，但不會付錢；用免費工具湊合」 | 關掉付費牆，偶爾回來看看 |
| 3–4 | 「無所謂，免費工具就夠了」 | 從來不打開這個功能 |
| 1–2 | 「我根本沒注意到有這個功能」 | — |

## 三個層次的證據

產品越接近上線，分數就越可靠：

| 階段 | 方法 |
|---|---|
| 撰寫規格時 | 價格敏感度問題、消失測試、免費替代測試 |
| Beta 測試及上線後 | 多少使用者在用這個功能、多常回來用，以及在沒有引導的情況下用得多深 |
| 上線後 | 真金白銀：碰到付費牆時有多少人轉換，以及降級時大家最常提到哪個功能 |

## 實際結果：分數改變了什麼

我們用涵蓋六種使用者類型的 100 位模擬使用者，為八個核心功能評分。有兩項發現改變了產品：

- **新聞只拿到 1.7 分（滿分 10），是所有功能中最低的。** 新聞到處都免費，沒人會為它付錢。於是我們從新聞轉向深度文章，深度文章還能帶來搜尋流量。
- **價值最高的兩個功能剛好互補。** 一個（每日選股建議）最受新手重視，專家比較不在意；另一個（股票評級）則正好相反。兩者合起來涵蓋了所有類型的使用者，因此成為付費方案的核心。

第三項發現：AI 搜尋對有經驗的使用者確實有價值，但速度太慢，所以 NPS 是負的。解法不是做新功能，而是讓現有功能變快。

## 價值不等於轉換

價值分數高，不代表就有同樣比例的使用者會付費。有三件事會把它打折：
1. **現實中的摩擦**，例如載入時間、分心、不想付錢：假設只有理論值的 50–70%
2. **每一步的流失**：下載 → 活躍 → 碰到付費牆
3. **價格**：小額單次付費和年費方案的轉換率可能差 3–5 倍

## NPS 評分：五個面向

為了估算每次改動會如何影響 NPS，每個版本都依照五個加權面向評分：

| 面向 | 權重 |
|---|---|
| 第一印象 | 0.15 |
| 內容品質 | 0.25 |
| 個人化 | 0.20 |
| 付費意願 | 0.25 |
| 回訪理由 | 0.15 |

每個規劃中的功能都會預估它在各面向上的變化，加總起來就是預期的 NPS 變化。在四次每週發布中，模擬 NPS 從 **−50 提升到 +28**，在最後針對過度樂觀做修正之前，一度達到 +40（見 [AI 模擬使用者測試](../ai-user-simulation/README.md)）。

## 每次發布如何運用

每個重要功能在決策紀錄中都要寫三行：
- **價值：** 用一句話說明為什麼有人會付錢
- **NPS 假設：** 預期範圍，以及我們要怎麼驗證
- **淘汰規則：** 上線 4 週後要衡量什麼，以及低於哪個水準就移除

之所以要有淘汰規則，是因為團隊很難刪掉自己做出來的東西。在上線前先決定門檻，就能把情緒排除在外。
